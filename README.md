# trusted-profit-agent

### 수익성 의사결정 Agent

> 기업 재무 데이터를 분석해 **이익이 왜 변했는지** 진단하고
> CEO가 **무엇을 결정해야 하는지**를
> 근거·반대증거·**결론이 바뀌는 조건**과 함께 제시한다.
> 데이터가 갱신되면 보고 우선순위와 대응 방안을 재평가한다.

**현재 상태:** 문제 정의 · 설계 · 데이터 검증 완료 → **구현 2026-07-28~29**
**제출:** 2026 제1회 Upstage × BDAI Harness Engineering Skillthon

---

## 1. 왜 이 문제인가

영리 기업이 내리는 의사결정은 **수익성의 극대화**를 지향할 것이다.
그래서 의사결정권자를 위한 AI Agent가 기여할 수 있는 가치를 보여주기 위해서는
**수익성에 영향을 미치는 지점**을 다뤄야 한다고 판단했다.

그리고 이 일은 사람보다 Agent가 잘할 수 있다.
**많은 데이터를 분석하고, 데이터의 관계 속에서 유의미한 맥락을 찾아내는 작업**이기 때문이다.

다만, 선택지만 나열하는 것은 의사결정을 돕는다고 보기 어렵다. Agent는 **자신의 판단이 틀리는 지점까지 파악하여, 결론이 바뀌는 Decision Boundary를 보여줄 수 있어야 한다.**

## 2. 공개 데이터에서 확인한 사항

대상은 재배포 가능한 공개 데이터 2종, **AdventureWorks**(Microsoft, MIT)와 **Contoso V2**(SQLBI, MIT)다. 전자는 제조·직판 중심 38개월치, 후자는 소매 유통 116개월치의 재무 데이터다. 업종이 다른 두 데이터에서 공통적으로 존재하는 데이터를 기반으로 Agent를 설계했다.

| | 두 데이터에 **공통으로 있는 것** | 그래서 계산할 수 있는 것 |
|---|---|---|
| 거래 | 라인 단위 수량 · 단가 · 원가 | 매출, 매출원가, **매출총이익** |
| 제품 | 제품 식별자 + 카테고리 계층 | 제품구성(믹스) 효과 |
| 고객 | 고객 식별자 + 거래 이력 | 반복구매·이탈 관점 |
| 기간 | 거래 일자 | 기간 비교, 추세 |
| 가격 | 할인 정보(형식은 다르나 양쪽 모두 분리 가능) | 실현가격, 할인 누수 |

| | 두 데이터에 **공통으로 없는 것** | 그래서 계산할 수 없는 것 |
|---|---|---|
| 판매관리비 | 없음 | 영업이익 · EBITDA 계열 분석 |
| 변동비 · 고정비 구분 | 없음 | 공헌이익 · **CVP 손익분기점** |
| 예산 · 목표 | 기준 단위가 서로 다름(한쪽은 영업사원별, 다른 쪽은 제품·매장별) | 계획 대비 실적 분석 |
| 재고 | 한쪽에만 있음 | 재고 기반 수익성 분석 |

> **이 제품군의 이익 변화는 판가 · 원가 · 제품구성 중 어디서 비롯되었는가.
> 그리고 대응 방안을 지금 결정할 것인가, 더 지켜볼까.**

이 Agent는 현상 파악을 넘어 대응 방안을 제시하며 CEO의 조치를 유도한다.

### 분해 방식은 관리회계의 표준 체계를 따른다

이익 변화를 원인별로 나누는 일은 임의로 만든 계산이 아니라, 관리회계의 **매출차이분석(Sales Variance Analysis)**이 오래 다뤄온 문제다.

```
매출총차이 = 매출가격차이 + 매출조업도차이
                            └→ 매출배합차이 + 매출수량차이
```

여기에 **단위원가 변동**을 더해 매출총이익의 변화를 원인별로 나눈다. 각 항목은 정의가 표준화되어 있어, 결과를 받는 사람이 계산 근거를 검증할 수 있다.

> **단 표준과 두 가지가 다르다.** 표준 매출차이분석은 **예산** 대비 **공헌이익**을 본다. 이 Agent는 **전기 실적** 대비 **매출총이익**을 본다. 공개 데이터에 예산과 변동비 구분이 없기 때문이다. **산출물에도 이 전제를 함께 표기한다.**

## 3. 이 Agent를 쓰기 위한 최소 조건

기업 데이터라면 무엇이든 넣어서 되는 것이 아니다. **아래 조건을 만족하는 데이터여야 한다.**

### 필수 — 없으면 작동하지 않는다

| 조건 | 왜 필요한가 |
|---|---|
| **거래 라인 단위** 데이터 | 집계된 손익만으로는 **조합별 탐색이 불가능**하다. 상쇄로 가려진 구간을 찾는 것이 이 Agent의 핵심이라, 라인 단위가 없으면 값어치가 사라진다 |
| 거래일자 · 제품 식별자 · 수량 · 단가 · **단위원가** | 원가가 없으면 마진 자체를 계산할 수 없다 |
| **두 기간 이상** | 변동분석은 당기·전기 비교다. 단일 시점으로는 불가능하다 |

### 있으면 분석이 깊어진다 — 없어도 부분 작동한다

| 조건 | 없으면 무엇이 빠지나 |
|---|---|
| 고객 식별자 | **§4 전체가 빠진다.** 마진 분해는 되지만 *"가격 문제인가 고객 문제인가"*를 구분할 수 없다 |
| 제품 카테고리 계층 | 제품구성 효과를 계층별로 볼 수 없다 |
| 할인 정보 | 실현가격·할인 누수를 분리할 수 없다 |
| 통화 · 환율 | 환율 효과를 분리할 수 없다 |

### 작동하지 않는 입력

- 집계된 손익계산서만 있는 경우
- 단일 기간 데이터
- 원가 정보가 없는 매출 데이터
- **예산·목표 대비 분석을 기대하는 경우** — 이 Agent는 전기 대비 변동만 다룬다

> 위 조건은 **설계 기준**이다. 최소 기간 길이·행수 하한 같은 수치 기준은 [Scaffolding.md](Scaffolding.md)의 `D3`·`D12`에서 확정한다.

## 4. 고객 데이터를 결합하는 이유

마진 분해는 **"무엇이 변했나"까지만** 답한다. 가격이 내렸는지, 원가가 올랐는지, 많이 팔았는지, 잘 팔리는 제품 구성이 바뀌었는지.

**여기에 구조적인 사각지대가 있다.** 마진 등식은 **수량을 하나의 숫자로만** 다루기 때문에, 그 숫자가 왜 줄었는지는 등식 밖의 문제다. 두 공개 데이터가 모두 **고객 식별자와 거래 이력**을 갖고 있다는 사실이 여기서 결정적이다. 같은 매출·이익 감소를 놓고 아래 네 가지를 구분할 수 있게 해준다.

| 질문 | 마진식만으로 | 고객 데이터를 결합하면 | 대응이 갈리는 지점 |
|---|---|---|---|
| 수량이 줄었다 — **비싸서 안 산 것인가, 고객이 떠난 것인가** | 구분 불가 (둘 다 "수량 감소") | 이탈 고객 수와 잔존 고객의 구매량을 분리 | **가격 정책** vs **고객 관계** |
| **소수 대형 고객이 떠났나, 다수 소액 고객이 떠났나** | 보이지 않음 | 고객별 기여도 분포로 집중도 판정 | **핵심 거래처 방어** vs **채널·유입 구조 개선** |
| **떠난 고객이 이익에 기여하던 고객인가** | 보이지 않음 | 고객별 마진을 결합해 이탈의 이익 영향 산출 | **되찾을 가치가 있는가**의 판단 근거 |
| **신규 유입이 줄었나, 기존이 떠났나** | 보이지 않음 | 첫 거래 시점으로 신규·기존 분리 | **획득** vs **유지** 중 어디에 쓸 것인가 |

같은 매출 감소라도 위 네 경우의 **대응은 서로 다르다.** 원인을 하나로 뭉쳐 보고하면 CEO는 잘못된 곳에 자원을 쓴다.

두 데이터의 **반복 구매 비율은 각각 37.1%와 93.4%** — 시장 성격이 극단적으로 다르다. 같은 판정 로직이 이 두 곳에서 모두 작동한다면, 그것이 일반화의 근거가 된다.

**단, 규율 하나를 함께 지킨다.**

> **마진 분해와 중복되는 고객 신호는 쓰지 않는다.**

고객 데이터를 쓰는 것 자체가 목적이 아니다. **마진식이 답하지 못하는 것만** 고객 데이터에 묻는다. 실제로 이 규율 때문에 후보 하나를 걸러냈다(아래 §9 참조).

## 5. 의사결정의 범위 판단

가장 유력한 원인을 짚어주기만 한다면 계산기와 다름 없다.

> "원가가 주범인 건 알겠다. **그런데 그 판단이 틀릴 수 있는 조건은 무엇인가?
> 지금 움직여야 하나, 한 분기 더 봐야 하나?**"

이 Agent는 결론과 함께 **그 결론이 뒤집히는 조건**을 제시한다.

- 원가가 얼마나 더 오르면 권고가 바뀌는가
- 판가를 얼마나 내리면 지금의 결론이 무효가 되는가
- 수량이 어느 선까지 회복되면 대응이 불필요해지는가

여기서 임의의 임계치를 쓰지 않는다. 대신 **권고가 뒤집히는 지점을 데이터에서 역산한다.** 경계까지 남은 여유(headroom)가 곧 그 판단의 확신도가 된다.

## 6. Skill — 무엇을 어떻게 자동화하나

분석 과정 전체를 **명령 하나로 재실행할 수 있는 단위**로 묶는다. 사람이 중간에 판단을 끼워 넣지 않아도 처음부터 끝까지 흐른다.

```
DecisionRequest  →  EvidenceBundle  →  HypothesisScore  →  DecisionCard
   (무엇을 물었나)     (근거 데이터)      (가설별 점수)      (결정 카드)
```

| 요구 | 이 Skill의 답 |
|---|---|
| **입출력이 명확한가** | 위 4단계가 계약이다. 각 단계는 JSON으로 주고받고 `schema_version`을 갖는다 |
| **재현되는가** | 계산은 전부 코드가 한다. **같은 입력이면 같은 결과**가 나온다. LLM은 설명 문장만 쓰고 숫자를 바꾸지 못한다 |
| **자동화되는가** | 데이터 변환 → 검증 → 마진 분해 → 가설 점수 → 경계 역산 → 카드 생성이 한 번의 실행으로 이어진다 |
| **검증은** | 별도 절차가 아니라 **Skill의 일부**다. 스키마·기간·키 중복·산식 대사를 확인해 `ValidationReport`를 함께 낸다. 원가 결측 같은 문제는 숨기지 않고 결과물의 *미확인(Unknowns)* 항목에 반영한다 |
| **두 데이터에서 같은가** | 데이터셋마다 어댑터가 다르지만 **그 뒤는 같은 코드**다. 두 데이터가 같은 필드를 산출하는 것이 완료 조건이다 |

> 구현은 2026-07-28~29에 진행한다. **입출력 계약의 필드 명세는 [Scaffolding.md](Scaffolding.md)의 D9에서 확정한다.**

## 7. Agent — 언제 돌고 무엇을 내놓나

Skill이 *한 번의 분석*이라면, Agent는 **그 분석을 계속 돌리며 판단을 갱신하는 층**이다.

**트리거** — 새 데이터가 들어오거나 정해진 시점이 되면 스스로 실행한다.

**루프** — `감지 → Skill 실행 → 이전 결과와 비교 → 저장 → 알림`. 이 루프는 **사람 없이 완주한다.**

**사람이 필요한 사안은 어떻게 다루나** — 승인이 필요한 결정을 자동으로 확정하지는 않는다. 다만 **그 때문에 루프를 멈추지도 않는다.** Agent는 계속 돌면서 결과물에 *"이 항목은 사람의 결정이 필요하다"*를 표시한다.

> **Agent는 사람이 없어도 계속 돈다. 다만 사람이 결정해야 할 것을 표시한다.**

**산출물** — 같은 판단 결과를 여러 양식으로 낸다. 문서 종류마다 분석을 새로 하지 않고, **하나의 `DecisionCard`를 서로 다른 서식으로 렌더링**한다.

| 산출물 | 근거 양식 |
|---|---|
| CEO Decision Card · 1p 브리핑 | 결론 · 근거 · 반대증거 · 경계 · 미확인 |
| 요건 정의서 | [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) BRS — 요구사항을 `[조건][주체][행동][객체][제약]` 5요소로 구성 |
| 제안서 | Barbara Minto, *The Pyramid Principle* — SCQA (결론 먼저) |
| 보고서 | Amazon 6-pager — 서술형 본문 + 데이터는 부록, 본문이 부록을 참조 |

**재판정** — 데이터가 갱신되면 이전 결과와의 차이를 산출물에 남긴다. 같은 데이터를 다시 받으면 중복 처리하지 않는다.

> 트리거 조건과 상태 관리 방식은 [Scaffolding.md](Scaffolding.md)의 D10·D11에서 확정한다.

## 8. 설계 원칙

| 원칙 | 이유 |
|---|---|
| **계산은 코드, 설명은 LLM** | LLM이 수치를 지어내지 못하게 한다. 계산 결과는 재현 가능해야 한다 |
| **검증을 산출물의 일부로** | 스키마·기간·키 중복·산식 대사를 `ValidationReport`로 함께 낸다 |
| **모르는 것은 모른다고 쓴다** | 계산 범위를 벗어난 값은 추정하지 않고 **미확인(Unknowns)**으로 표시한다 |
| **같은 입력은 같은 결론** | 실행할 때마다 권고가 흔들리면 의사결정 도구가 아니다 |
| **설명할 수 없으면 채택하지 않는다** | 통계적으로 우수해도 판단 근거를 사용자가 설명하지 못하면 제외한다 |

## 9. 스스로 깬 전제

이 프로젝트에서 가장 많은 시간을 쓴 일은 **스스로 세운 전제를 검증하고 기각하는 것**이었다.

### "두 데이터에서 원가는 같은 뜻이다" → 기각

양쪽 모두 단위원가 컬럼이 있으니 공통 스키마로 묶을 수 있다고 봤다.
검산 결과 **정의가 달랐다.** 한쪽은 제품 마스터의 **표준원가**(계획된 원가), 다른 쪽은 판매 거래에 기록된 **실제 거래원가**다.
같은 필드로 적재하면 원가 차이를 마진 변동으로 오해하게 된다.

→ 공통 스키마를 포기하고, **원가의 의미를 메타데이터(`cost_basis`)로 명시**하는 구조로 전환했다.

### "활성 고객 수 추세를 보조 지표로" → 철회

마진과 다른 각도를 보여줄 지표로 채택하려 했다. 검증 결과 **주문 건수와 상관계수 0.999969 / 0.999258**.
사실상 같은 정보의 반복이었다.

→ 철회하고, 대체 지표를 **과거 구간 학습 · 이후 구간 검증(holdout)** 방식으로 판정 중이다.
기준 모형(직전 기간 · 전년 동기)보다 나은 예측력을 보이지 못하면 채택하지 않는다.
