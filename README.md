# trusted-procurement-agent

### 식자재 조달 **점검 우선순위**를 정하는 Agent

> 매일 아침, 취급 품목 전부를 훑어 **"오늘 먼저 봐야 할 것"** 몇 개를 골라
> *왜 이상한지 · 얼마나 갈지 · 대체할 게 있는지 · 어디가 싼지*를 근거와 함께 한 장으로 낸다.

**쓰는 사람** — 기업의 **구매·조달 담당자**. 매일 수십 품목의 시세를 확인해야 하지만 전부 볼 시간은 없는 사람.

> **왜 「결정」이 아니라 「점검 우선순위」인가** — 조달 결정은 시장가격만으로 내려지지 않는다.
> 계약가격·구매량·재고·사용속도 같은 **내부 정보**와 품질규격·납기실적·대체 공급처 같은 **공급자 정보**가 함께 필요한데,
> 공공데이터에는 **외부 정보(시장가격·물량·지역·계절)밖에 없다.**
> 그래서 결정을 대신하지 않고, **결정 전에 무엇을 먼저 검토해야 하는지**를 정한다. 이것이 현재 데이터로 정직하게 도달할 수 있는 지점이다.

**현재 상태:** 데이터 소스 확정 · 실측 검증 완료 → **구현 2026-07-28~29**
**제출:** 2026 제1회 Upstage × BDAI Harness Engineering Skillthon

## 1. 왜 조달인가

조달 의사결정에 AI Agent가 강점을 가지는 이유는 다음과 같다.

| 조건 | 이유 |
|---|---|
| 반복 | 매입은 주 단위·월 단위로 계속된다 |
| 판단 근거 | 직관과 관행이 아니라, 데이터로 설명한다 |
| 독립성 | 외부의 공개데이터를 활용한다 |

마지막 조건이 결정적이다. 각기 다른 기업의 내부 데이터에 의존하지 않고 일관성 있는 서비스를 제공할 수 있는 Agent를 만들고 싶었다.

## 3. 쓰는 사람이 묻는 것

**갈래를 데이터에서 역산하지 않는다.** 식자재를 사는 사람이 실제로 하는 고민에서 출발하고, 각 질문에 데이터가 어디까지 답하는지를 붙인다.

| # | 조달 담당자의 질문 | 우리가 답하는 것 | 근거 데이터 |
|---:|---|---|---|
| **1** | *"이번 주 뭐가 비싸졌지?"* | 전 지원 품목을 훑어 **평년 대비 이탈이 큰 품목**을 골라낸다 | 가격 3년 시계열 |
| **2** | *"이 가격이 비싼 건가?"* | 같은 등급·시장 기준에서 **평년 어디쯤인지, 몇 배인지** | 가격 · 등급 · 시장 |
| **3** | *"얼마나 갈까? 지금 사야 하나?"* | 🔑 **과거에 같은 수준으로 오른 적이 몇 번이고 각각 며칠 갔는지** | 가격 3년 시계열 |
| **4** | *"대신 쓸 게 있나?"* | 🔑 **대체 가능한 품목의 현재 가격을 나란히** — 배추가 2배면 양배추는 어떤가 | 가격 · 품목 분류 |
| **5** | *"어디서 사면 싼가?"* | **시장·지역 간 가격차와 유통 단계 차이**(중도매↔소매) | 시장 217 · 지역 39 |

**3번과 4번이 이번에 새로 들어왔다.** 지금까지 우리는 *"데이터로 뭘 할 수 있나"*에서 갈래를 뽑았고, 그래서 **사는 사람이 가장 자주 하는 두 질문이 빠져 있었다.**

### 3번이 「언제」를 대신한다 — 예측이 아니라 과거 사례 참조

*"지금 사야 하나"*에 답하는 방법은 두 가지다.

| | 방법 | 성립하는가 |
|---|---|---|
| ❌ | **예측** — 기상·수입으로 앞으로의 가격을 맞힌다 | **기각.** 30일 누적 기상 지표가 가격 급등과 대응하지 않았다(§4) |
| ⭕ | **과거 사례 참조** — *"평년의 2배를 넘은 적이 3년간 3번 있었고 각각 21일·18일·2일 지속됐다"* | **성립.** 관측된 사실의 요약이라 선행성 검증이 필요 없다 |

두 번째는 **판단을 사용자에게 남긴다.** *"지난번엔 3주 갔다"*를 보고 지금 살지 기다릴지는 사람이 정한다. 우리가 *"사라/기다려라"*라고 말하지 않으면서도 **시점 판단에 필요한 근거는 준다.**

### 🔴 「업무 영향」은 우리만으로 계산되지 않는다

가격이 두 배로 올라도 **내가 안 쓰는 품목이면 볼 필요가 없다.** 실제 우선순위는 이렇게 정해진다.

```
업무 영향 = 가격 이상  ×  내 구매량  ×  재고 소진 위험  ×  대체 가능성
             ─────────                                    ─────────
             우리가 안다                                   우리가 안다
                         ───────────────────────────
                         내부 정보 — 공공데이터에 없다
```

**네 요소 중 둘만 우리 손에 있다.** 그래서 산출물은 *"이것이 당신에게 얼마나 중요하다"*가 아니라 **"이것이 평소와 다르니 당신이 판단하라"**에 머문다.

다만 **취급 품목 목록만 받으면 절반은 메워진다.** 매입가처럼 매번 입력할 필요가 없고 한 번 등록하면 잘 바뀌지 않는다 — 그래서 §4의 층 구조를 매입가가 아니라 **품목 목록**을 기준으로 다시 잡았다.

### 답하지 않는 것

| 질문 | 왜 답하지 않나 |
|---|---|
| *"이 품목을 계속 취급할까"* | 내부 수익성 데이터가 필요하다 |
| *"적정가는 얼마인가"* | 규범적 기준이 없다. **분포상 위치**만 말한다 |
| *"앞으로 오를까 내릴까"* | 예측 근거를 확보하지 못했다(위 표) |
| *"이만큼 사두면 된다"* | 소비량·보관 능력을 모른다 |
| *"이 공급처가 믿을 만한가"* | 품질규격·납기실적 데이터가 없다 |
| *"원산지·이력이 확실한가"* | 시세 데이터에 이력추적 정보가 없다 |

## 4. 산출물 — 시장 보고서가 아니라 **예외 보고 한 장**

매일 전 품목 시세표를 주면 읽지 않는다. **오늘 이상한 몇 개만** 정해진 순서로 낸다.

| 순서 | 항목 | 우리가 채우는 것 |
|---:|---|---|
| 1 | **우선 검토 품목** | 평년 대비 이탈이 큰 순으로 상위 몇 개 |
| 2 | **이상 근거** | 평년의 몇 배인가 · 며칠째인가 · 어느 등급·시장 기준인가 |
| 3 | **예상 영향** | ⚠️ **부분만.** 품목 목록이 있으면 *"취급 품목 중 N개 해당"*, 없으면 미판정 |
| 4 | **가능한 대응** | 대체 품목의 현재 가격 · 더 싼 시장·지역 · 유통 단계 전환 |
| 5 | **추가 확인 사항** | 🔑 **우리가 모르는 것을 명시한다** — 재고·계약가·납기·공급처 |
| 6 | **판단 시한 참고** | 과거 같은 수준의 급등이 며칠 지속됐는지 |

**3번과 5번이 이 산출물의 성격을 정한다.** 우리는 *"이것이 당신에게 얼마나 중요하다"*를 말하지 않고, **무엇을 확인해야 판단할 수 있는지**를 알려준다.

### 층 구조 — 입력이 없어도 완주한다

```
[0층 · MVP · 입력 없음]        지원 품목 전체에서 이상 품목을 골라낸다
                                → 누가 실행하든 같은 결과. 항상 나온다

[1층 · MVP · 품목 목록만]      "내가 쓰는 품목" 목록을 한 번 등록하면
                                → 그 안에서만 골라내고, 예상 영향의 절반이 채워진다
                                → 목록은 자주 바뀌지 않아 매번 입력할 필요가 없다

[2층 · MVP 범위 밖]            매입가까지 넣으면
                                → 내 가격이 시장 분포 어디인지 판정
                                → 1층이 정상 작동하는 것을 확인한 뒤 착수
```

> **이전 설계에서 바뀐 점** — 원래 2층의 입력을 *매입가*로 잡았는데, **품목 목록이 먼저다.**
> 매입가는 품목마다 계속 바뀌지만 **취급 품목은 한 번 등록하면 오래 간다.** 입력 부담이 훨씬 낮으면서 얻는 것은 더 크다.

**0층만으로 MVP가 성립한다.** 0층은 *조회*가 아니라 **선별**이다 — 무엇을 물어야 할지 모를 때 **시스템이 볼 것을 정해준다.** 평가 기준의 *"단순 조회를 넘었는가"*가 여기서 갈린다.

### 🔴 「공급위험 신호」는 실측 결과 현재 방법으로는 성립하지 않는다

산출물에 *"주산지 기상 이상"*을 넣으려 했으나 **재보니 대응하지 않았다.** 배추 가격이 평년 대비 1.5배 이상 오른 구간을 찾고, 그 직전 30일 주산지 기상을 **같은 날짜의 다른 연도와 대조**했다.

| 사건 | 지역 | 급등한 해 | 급등 없던 해 |
|---|---|---|---|
| 2024-09 파동 (평년 2.09배) | 태백 | 특보 **0건** | 2023: 1건 · 2025: **2건** |
| 2025-01 급등 (평년 2.35배) | 태백 | 특보 12건 | 2024: **19건** |
| 2023-08 급등 (평년 1.65배) | 서산 | 강수 445mm | 2025: **1,117mm** |

**세 사건 모두 대조군이 기상이 더 나쁜데 가격은 오르지 않았다.** 30일 누적 강수·기온·특보 어느 지표로도 갈리지 않는다.

짐작되는 이유는 **시점**이다. 배추 가격은 출하 시점 날씨가 아니라 **몇 달 전 정식 시기의 조건과 재배면적**에 좌우되는데, 우리에게 면적·생산량 데이터가 없다.

> **다만 기상 데이터를 버리지 않는다.** 13개 연도가 확보돼 있고, 확인된 것은 *"30일 누적 지표로는 안 된다"*이지 *"기상이 무용하다"*가 아니다.

## 5. 세 소스가 실제로 이어붙는다 — 배추로 입증

```
가격  품목 211 배추 · 품종 02 여름(고랭지) · 등급 상품
      2025-10-01  가락도매 중도매  27,700원/kg
기상  AREA_ID 4219000000 태백 × PA170301 배추(고랭지)
      2025-10-01  평균 15℃ · 강수 0mm · 일조 8h
수입  HS 0704902000 배추
      2025.10  수입 2,327,698kg / 789,767달러
```

**공통 구간은 2014~2026, 13개 연도다.**

### 정확한 대응을 위한 설계

세 소스의 품목 체계가 서로 다르다(자체 품목코드 · HS코드 · 작물 특성 ID). 문자열 매칭으로 처리하면 **즉시 틀린다.**

| 잘못된 대응 | 왜 틀렸나 |
|---|---|
| `PA240201` ← `"배추"` 검색 결과 | 실제로는 **양배추(고랭지)**다. `"배추" in "양배추"`가 참이라 걸렸다 |
| `PA170401` 배추(가을) ← 10월이니까 | 10월 **가격**의 품종은 `여름(고랭지)`다. 계절 이름이 서로 다른 것을 가리킨다 |

**배추 하나에 주산지 특성 ID가 9개 있고 계절로 갈린다.** 그래서 대응 키는 품목명이 아니라 **품목 + 계절(품종)**이며, **사람이 만든 대응표**가 필요하다. 지금 검증된 대응은 배추 하나뿐이고, 나머지는 수집 대상을 좁힌 뒤 품목마다 실제 응답으로 검증한다.

## 6. Skill — 무엇을 자동화하나

분석 과정 전체를 **명령 하나로 재실행할 수 있는 단위**로 묶는다. 사람이 중간에 판단을 끼워 넣지 않아도 처음부터 끝까지 흐른다.

| 요구 | 이 Skill의 답 |
|---|---|
| **입출력이 명확한가** | 단계마다 JSON으로 주고받고 `schema_version`을 갖는다. **필드 명세는 구현 착수 전에 확정한다** |
| **재현되는가** | 계산은 전부 코드가 한다. LLM은 설명한다. |
| **자동화되는가** | 수집 → 검증 → 평년 기준선 산출 → 이탈 품목 선별 → 대체·시장 비교 → 예외 보고 생성이 한 번의 실행으로 이어진다 |
| **검증은** | 별도 절차가 아니라 **Skill의 일부**다. 스키마·기간·키 중복·단위를 확인해 검증 보고서를 함께 낸다. 미조사일·미매칭 품목은 숨기지 않고 결과물의 *미확인* 항목에 반영한다 |
| 🔑 **키 없이도 도는가** | **`sample-data/`에 수집 스냅샷을 넣어 인증키 없는 환경에서도 전 과정이 실행된다.** 재현 가능성을 소스 선정 조건으로 삼은 것과 같은 이유다 |

**표준 폴더 구조를 따른다.**

```
skills/data-analysis/
├── skill.md          스킬 설명 및 사용법
├── README.md         개발자용 문서
├── reference/        지표·판정 규칙 정의
├── scripts/          collect · clean · analyze · plot
├── templates/        산출물 서식
├── examples/         사용 예시
├── sample-data/      수집 스냅샷 (키 없이 실행용)
└── config/           수집 범위·판정 기준 설정
```

## 7. Agent — 언제 돌고 무엇을 내놓나

Skill이 *한 번의 분석*이라면, Agent는 분석을 반복하며 판단을 갱신한다.

**트리거** — 새 시세가 갱신되거나 정해진 시점이 되면 스스로 실행한다. 본체 소스가 일별 갱신이므로, 별도의 트리거가 필요 없다.

**루프** — `감지 → 수집 → Skill 실행 → 이전 결과와 비교 → 저장 → 알림`. 이 루프는 Agent가 혼자 완주한다.

**사람이 필요한 사안은 어떻게 다루나** — 승인이 필요한 결정을 자동으로 확정하지 않는다. 다만 **그 때문에 루프를 멈추지도 않는다.**

> **Agent는 사람이 없어도 계속 돈다. 다만 사람이 결정해야 할 것을 표시한다.**

**재평가** — 데이터가 갱신되면 이전 결과와의 차이를 산출물에 남긴다. 같은 데이터를 다시 받으면 중복 처리하지 않는다.

## 8. 설계 원칙

| 원칙 | 이유 |
|---|---|
| **계산은 코드, 설명은 LLM** | LLM이 수치를 지어내지 못하게 한다. 계산 결과는 재현 가능해야 한다 |
| **검증을 산출물의 일부로** | 스키마·기간·키 중복·단위를 확인해 검증 보고서를 함께 낸다 |
| **모르는 것은 모른다고 쓴다** | 재지 않은 것을 확정값처럼 쓰지 않는다. **「미측정」·「원인 미상」을 그대로 표기한다** |
| **같은 입력은 같은 결론** | 실행할 때마다 권고가 흔들리면 의사결정 도구가 아니다 |
| **설명할 수 없으면 채택하지 않는다** | 통계적으로 우수해도 판단 근거를 설명하지 못하면 제외한다 |
| **재현할 수 없는 데이터는 쓰지 않는다** | 제3자가 자기 키로 같은 데이터를 받을 수 있어야 한다 |
