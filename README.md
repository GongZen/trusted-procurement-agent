# trusted-procurement-agent

### 식자재 조달 의사결정 지원 Agent

> 공공데이터로 **농·축·수산물 시세를 실시간으로 추적**해
> *"어떤 품목이 평소와 다른 가격인지 · 이 가격이 어느 정도 수준인지 · 공급 측에 무슨 이슈가 있는지"*를 파악하여
> 조달 의사결정에 대한 조언과 근거를 제시한다.

**쓰는 사람** — 음식점을 운영하는 자영업자, 식품조리·급식 기업의 의사결정자.
**현재 상태:** 데이터 소스 확정 · 실측 검증 완료 → **구현 2026-07-28~29**
**제출:** 2026 제1회 Upstage × BDAI Harness Engineering Skillthon

---

## 1. 왜 조달인가

조달 의사결정에 AI Agent가 강점을 가지는 이유는 다음과 같다.

| 조건 | 이유 |
|---|---|
| 반복 | 매입은 주 단위·월 단위로 계속된다 |
| 판단 근거 | 직관과 관행이 아니라, 데이터로 설명한다 |
| 독립성 | 외부의 공개데이터를 활용한다 |

마지막 조건이 결정적이다. 각기 다른 기업의 내부 데이터에 의존하지 않고 일관성 있는 서비스를 제공할 수 있는 Agent를 만들고 싶었다.

### 품질 진단 — 배추 3년 전량 48,240건

| 연도 | 수신/전체 | 평일 조사일/평일 | 커버리지 | 핵심 컬럼 10개 결측 | 중복 키 | 가격 이상값 |
|---|---|---|---|---|---|---|
| 2023 | 16,817 / 16,817 | 245 / 260 | 94.2% | 0건 | 0건 | 0건 |
| 2024 | 15,447 / 15,447 | 244 / 262 | 93.1% | 0건 | 0건 | 2건 |
| 2025 | 15,976 / 15,976 | 242 / 261 | 92.7% | 0건 | 0건 | 0건 |

미조사일은 품목별 결측치가 아니라 조사 자체가 없는 날이다. 부류가 다른 네 품목(배추·쌀·사과·고등어)의 조사일 집합을 대조했더니 교집합 = 합집합으로 완전히 일치했다(품목 간 차이 0일). 날짜도 설·추석·삼일절·현충일·광복절·개천절·한글날·성탄절·선거일·임시공휴일과 일치한다.

다만 매년 12월 초 하루(2023-12-01 · 2024-12-06 · 2025-12-05)는 공휴일이 아님에도 불구하고 데이터가 없다. 원인을 확인하지 못해 원인 미상으로 남겼다.

### 수집 규모가 일 트래픽을 넘는다

12품목을 실측했더니 품목 간 편차가 크다.

| 품목 | 2025년 행 수 | | 품목 | 2025년 행 수 |
|---|---|---|---|---|
| 소 | 92,136 | | 배추 | 15,976 |
| 쌀 | 29,222 | | 참깨 | 12,373 |
| 고등어 | 28,436 | | 닭고기 | 930 |
| 사과 | 26,766 | | 표고버섯 | 749 |

**12품목에서 잰 값을 136품목 3년치로 늘려 잡으면 9,792 ~ 37,944요청**인데 개발계정 일 트래픽은 10,000회다. 전 품목 3년치를 하루에 받을 수 없다. 수집 범위(품목 수·기간)를 좁히거나 여러 날에 나눠야 하며, 이 제약은 Skill 입출력과 함께 잠근다.

> 🔑 **쓰는 사람이 정해지면서 범위를 좁힐 첫 근거가 생겼다.** 특용작물 부류의 **화훼 6품목**(국화·카네이션·장미·백합·글라디올러스·튜울립)은 식자재가 아니므로 수집 대상이 아니다. 같은 기준으로 더 걸러낼 수 있다.

## 3. 데이터로 추론할 수 있는 것과 없는 것

기준마다 데이터로 추론할 수 있는 영역이 다르다.

| 기준 | 답하는 수위 | **답하지 않는 수위** |
|---|---|---|
| **무엇을** *선별* | *"지금 136품목 중 무엇이 평소와 다른가"* | *"이 품목을 계속 취급할까"* — 내부 수익성(내부 데이터)이 필요하다 |
| **얼마에** *가격 타당성* | *"이 가격이 같은 등급·시장 기준에서 어디쯤인가"* | *"적정가는 얼마인가"* — 회사의 자체적인 기준이 천차만별이다 |
| **언제** *공급 신호* | 🔴 **방법 재설계 중** (§4) | *"즉시 구매 / 보류"* — **재봤더니 30일 누적 기상 지표는 가격 급등과 대응하지 않았다** |

> **「무엇을」이 Agent의 시작이다.** 136품목 중 무엇을 볼지 정해지지 않으면 돌 대상이 없다.
> 이 갈래는 선택 사항이 아니라 **루프의 입력**이다.

> **「언제」는 아직 열려 있다.** 첫 접근(주산지 기상 30일 누적)은 실측에서 기각됐다(§4).
> 다만 기상 데이터 13개 연도가 확보돼 있으므로 **접근 방법을 바꿔 살릴 여지를 찾는 중**이다.
> 확인된 것은 *"이 방법으로는 안 된다"*이지 *"기상이 무용하다"*가 아니다.

## 4. 산출물은 2층 — 입력이 없어도 완주한다

```
[1층 · MVP · 항상 산출]   공공데이터만으로
    · 품목별 시장 기준가격과 분포 (최저·중앙·최고, 등급별)
    · 평년(과거 같은 달) 대비 위치 — 몇 배인가
    · 전일·전주·전년 동기 대비 변화
    · 지역 간 가격 격차 · 유통 단계 간 차이
    → 여기서 "평소와 다른 품목"을 골라낸다

[2층 · MVP 범위 밖]   사용자 매입가를 얹어
    · 내 매입가가 시장 분포의 어디에 있는가
    → 1층이 정상 작동하는 것을 확인한 뒤에 착수한다
```

**1층만으로 MVP가 성립한다.** 1층은 *조회*가 아니라 **선별**이다 — 사용자가 무엇을 물어야 할지 모를 때, 136품목을 훑어 **지금 봐야 할 것을 시스템이 정해준다.** 평가 기준의 *"단순 조회를 넘었는가"*가 여기서 갈린다.

> **2층을 설계에서 지우지 않는 이유** — *"내 가격과 비교해달라"*는 당연한 요구이고, 그 답을 미리 준비해두는 것이 확장 지점을 인식했다는 근거가 된다. 다만 **MVP에는 넣지 않는다.** 매입가를 어떤 형태로 받을지가 플랫폼 사양에 달려 있어, 미정인 것에 MVP를 걸 수 없다.

### 🔴 「공급위험 신호」는 실측 결과 현재 방법으로는 성립하지 않는다

1층에 *"주산지 기상 이상"*을 넣으려 했으나 **재보니 대응하지 않았다.** 배추 가격이 평년 대비 1.5배 이상 오른 구간을 찾고, 그 직전 30일 주산지 기상을 **같은 날짜의 다른 연도와 대조**했다.

| 사건 | 지역 | 급등한 해 | 급등 없던 해 |
|---|---|---|---|
| 2024-09 파동 (평년 2.09배) | 태백 | 특보 **0건** | 2023: 1건 · 2025: **2건** |
| 2025-01 급등 (평년 2.35배) | 태백 | 특보 12건 | 2024: **19건** |
| 2023-08 급등 (평년 1.65배) | 서산 | 강수 445mm | 2025: **1,117mm** |

**세 사건 모두 대조군이 기상이 더 나쁜데 가격은 오르지 않았다.** 30일 누적 강수·기온·특보 어느 지표로도 갈리지 않는다.

짐작되는 이유는 **시점**이다. 배추 가격은 출하 시점 날씨가 아니라 **몇 달 전 정식 시기의 조건과 재배면적**에 좌우되는데, 우리에게 면적·생산량 데이터가 없다.

> **다만 「언제」를 버리지 않는다.** 기상 데이터 자체는 확보돼 있고 13개 연도가 있다. **접근 방법을 바꿔 살릴 여지를 찾는 중이다.**
> 확인된 것은 *"30일 누적 기상 지표로는 안 된다"*이지 *"기상이 무용하다"*가 아니다.

## 5. 세 소스가 실제로 이어붙는다 — 배추로 입증

```
가격  품목 211 배추 · 품종 02 여름(고랭지) · 등급 상품
      2025-10-01  가락도매 중도매  27,700원/kg
기상  AREA_ID 4219000000 태백 × PA170301 배추(고랭지)
      2025-10-01  평균 15℃ · 강수 0mm · 일조 8h
수입  HS 0704902000 배추
      2025.10  수입 2,327,698kg / 789,767달러
```

**공통 구간은 2014~2026, 13개 연도다.**

### 정확한 대응을 위한 설계

세 소스의 품목 체계가 서로 다르다(자체 품목코드 · HS코드 · 작물 특성 ID). 문자열 매칭으로 처리하면 **즉시 틀린다.**

| 잘못된 대응 | 왜 틀렸나 |
|---|---|
| `PA240201` ← `"배추"` 검색 결과 | 실제로는 **양배추(고랭지)**다. `"배추" in "양배추"`가 참이라 걸렸다 |
| `PA170401` 배추(가을) ← 10월이니까 | 10월 **가격**의 품종은 `여름(고랭지)`다. 계절 이름이 서로 다른 것을 가리킨다 |

**배추 하나에 주산지 특성 ID가 9개 있고 계절로 갈린다.** 그래서 대응 키는 품목명이 아니라 **품목 + 계절(품종)**이며, **사람이 만든 대응표**가 필요하다. 지금 검증된 대응은 배추 하나뿐이고, 나머지는 수집 대상을 좁힌 뒤 품목마다 실제 응답으로 검증한다.

## 6. Skill — 무엇을 자동화하나

분석 과정 전체를 **명령 하나로 재실행할 수 있는 단위**로 묶는다. 사람이 중간에 판단을 끼워 넣지 않아도 처음부터 끝까지 흐른다.

| 요구 | 이 Skill의 답 |
|---|---|
| **입출력이 명확한가** | 단계마다 JSON으로 주고받고 `schema_version`을 갖는다. **필드 명세는 구현 착수 전에 확정한다** |
| **재현되는가** | 계산은 전부 코드가 한다. LLM은 설명한다. |
| **자동화되는가** | 수집 → 검증 → 기준가 산출 → 이상 신호 탐지 → 카드 생성이 한 번의 실행으로 이어진다 |
| **검증은** | 별도 절차가 아니라 **Skill의 일부**다. 스키마·기간·키 중복·단위를 확인해 검증 보고서를 함께 낸다. 미조사일·미매칭 품목은 숨기지 않고 결과물의 *미확인* 항목에 반영한다 |
| 🔑 **키 없이도 도는가** | **`sample-data/`에 수집 스냅샷을 넣어 인증키 없는 환경에서도 전 과정이 실행된다.** 재현 가능성을 소스 선정 조건으로 삼은 것과 같은 이유다 |

**표준 폴더 구조를 따른다.**

```
skills/data-analysis/
├── skill.md          스킬 설명 및 사용법
├── README.md         개발자용 문서
├── reference/        지표·판정 규칙 정의
├── scripts/          collect · clean · analyze · plot
├── templates/        산출물 서식
├── examples/         사용 예시
├── sample-data/      수집 스냅샷 (키 없이 실행용)
└── config/           수집 범위·판정 기준 설정
```

> 🔒 **입출력 계약은 구현 전에 잠근다.** 진행 구조와 제출 요건: [Scaffolding.md](Scaffolding.md)

## 7. Agent — 언제 돌고 무엇을 내놓나

Skill이 *한 번의 분석*이라면, Agent는 분석을 반복하며 판단을 갱신한다.

**트리거** — 새 시세가 갱신되거나 정해진 시점이 되면 스스로 실행한다. 본체 소스가 일별 갱신이므로, 별도의 트리거가 필요 없다.

**루프** — `감지 → 수집 → Skill 실행 → 이전 결과와 비교 → 저장 → 알림`. 이 루프는 Agent가 혼자 완주한다.

**사람이 필요한 사안은 어떻게 다루나** — 승인이 필요한 결정을 자동으로 확정하지 않는다. 다만 **그 때문에 루프를 멈추지도 않는다.**

> **Agent는 사람이 없어도 계속 돈다. 다만 사람이 결정해야 할 것을 표시한다.**

**재평가** — 데이터가 갱신되면 이전 결과와의 차이를 산출물에 남긴다. 같은 데이터를 다시 받으면 중복 처리하지 않는다.

이 프로젝트에서 가장 많은 시간을 쓴 일은 **스스로 세운 전제를 검증하고 기각하는 것**이었다.

### "완결된 공개 데이터셋으로 충분하다" → 주제를 통째로 바꿨다

처음에는 AdventureWorks·Contoso V2로 **수익성(마진) 진단 Agent**를 만들려 했다. 두 데이터는 거래 라인 단위로 수량·단가·원가가 분리돼 있어 매출차이분석이 가능했다.

**그런데 세 곳에서 막혔다.**

| 막힌 지점 | 내용 |
|---|---|
| 최신성 | 갱신되지 않는 완결 파일이라 *"새 데이터 감지"* 트리거를 **인위적으로 만들어야** 했다 |
| 외부 결합 | 가상 기업이라 어떤 공공데이터와도 **결합되지 않는다** |
| 표본 | AdventureWorks는 완전 연도가 두 개뿐이라 전년 대비 비교 조합이 **하나밖에** 없다 |

**근본 문제는 데이터가 아니라 순서였다.** 데이터를 바꾸는 대신 **질문을 데이터에 맞춰왔다.** 그래서 데이터 소스부터 다시 정하고, 그 데이터로 답할 수 있는 결정 유형(조달)을 골랐다.

기존 실측 결과는 폐기했지만 **판단 이력은 [DECISIONS.md](DECISIONS.md)에 유효/폐기 경계와 함께 남겼다.** 어떤 규칙이 데이터와 무관한 원칙이고 어떤 것이 스키마에 묶인 규칙이었는지 구분해 적었다.

### "갱신 주기가 실시간이면 과거 시계열이 있다" → 기각

[공영도매시장 실시간 경매정보](https://www.data.go.kr/data/15141808/openapi.do)는 경매 건 단위로 초 단위 낙찰 시각까지 주는, 가장 두꺼운 데이터였다. 문서상 갱신 주기는 *"실시간"*이다.

**호출해 보니 과거가 없었다.** 두 경로를 모두 확인했다.

| 조회 시점 | 농림축산식품 경로 | 공공데이터포털 경로 |
|---|---|---|
| 전일 | 있음 (119,729건) | **있음** |
| 2025년 12개월 전부 | 0 | **0** |
| 2024·2023·2022 | 파편적 | **전부 0** |

같은 날짜를 네 개 시장에 던져도 모두 0이었다. **이름이 이미 말하고 있었다** — *"실시간"*은 최근분을 흘려보내는 API이지 이력을 보관하는 API가 아니다.

→ **탈락시키고, 같은 계열의 일별 집계본(정산정보)으로 옮겼다.** 그쪽에는 과거가 남아 있다.

### "데이터 조건 6가지로 충분하다" → 7번째를 추가했다

교육자료의 좋은 데이터 6조건(목적 적합성·출처 신뢰성·최신성·완전성·일관성·충분한 표본)으로 소스를 판정하다가 **반나절을 잃었다.**

농림축산식품 공공데이터포털은 **신청 시 등록한 IP에서만** 응답한다. 6조건을 모두 통과한 소스가 **다른 사람 환경에서는 작동하지 않는다**는 사실이 판정 기준에 없었다.

→ **7번째 조건을 추가했다 — *"제3자가 자기 인증키로 같은 데이터를 받을 수 있는가"*.**
배점 절반이 동작에 걸려 있고 1차 심사가 *"스킬 동작 여부"*를 보는데, **내 PC에서만 도는 Agent는 동작하지 않는 Agent다.**

### "양쪽 포털에 다 있는지는 검색하면 안다" → 오판했다

정산정보를 농림축산식품 포털 전용으로 판정해 캐시로 강등했다. **교차 검토에서 뒤집혔다** — 공공데이터포털 상세 페이지에 자체 엔드포인트가 찍혀 있었고, 활용신청 후 호출하니 같은 데이터가 나왔다. 오히려 **공공데이터포털 경로가 더 길었다**(2018~ vs 2020~).

→ **규칙으로 고정했다.** *"양쪽에 있다"*를 검색 결과로 판단하지 않고 **상세 페이지의 End Point 표기**를 본다.

### "「무엇을」은 내부 수익성이 없으면 답할 수 없다" → 층을 나눠 살렸다

*"이 품목을 계속 취급할까"*는 내부 수익성이 필요해 답할 수 없다고 판단하고 갈래를 제외하려 했다. **그런데 그러면 Agent가 돌 대상이 없어진다.**

→ 두 층으로 나눴다. **선별**(*"지금 무엇을 봐야 하는가"*)은 외부 데이터만으로 성립하고, **취급 지속** 판단만 제외했다. 갈래를 없애는 대신 **답하는 수위를 낮췄다.**

## 9. 설계 원칙

| 원칙 | 이유 |
|---|---|
| **계산은 코드, 설명은 LLM** | LLM이 수치를 지어내지 못하게 한다. 계산 결과는 재현 가능해야 한다 |
| **검증을 산출물의 일부로** | 스키마·기간·키 중복·단위를 확인해 검증 보고서를 함께 낸다 |
| **모르는 것은 모른다고 쓴다** | 재지 않은 것을 확정값처럼 쓰지 않는다. **「미측정」·「원인 미상」을 그대로 표기한다** |
| **같은 입력은 같은 결론** | 실행할 때마다 권고가 흔들리면 의사결정 도구가 아니다 |
| **설명할 수 없으면 채택하지 않는다** | 통계적으로 우수해도 판단 근거를 설명하지 못하면 제외한다 |
| **재현할 수 없는 데이터는 쓰지 않는다** | 제3자가 자기 키로 같은 데이터를 받을 수 있어야 한다 |

## 한계

- **매입 시점을 권고하지 않는다.** 주산지 기상 30일 누적 지표는 가격 급등과 대응하지 않았다(§4 실측). 대체 방법을 찾는 중이며, **찾기 전까지 시점 권고를 하지 않는다.**
- **품목 취급 여부를 판단하지 않는다.** 기업 내부 데이터가 없다.
- **수요·소비량 데이터가 없다.** 두 포털에 존재하지 않는다. 소비자물가지수는 지수일 뿐 물량이 아니다.
- **정부 수급조절(비축·방출) 물량을 반영하지 못한다.** 가격에 직접 개입하는 변수인데 API가 없다.
- **품목 간 대응표가 배추 하나만 검증됐다.** 나머지는 수집 대상 확정 후 품목마다 실제 응답으로 검증한다.
- **전 품목 3년치를 하루에 수집할 수 없다.** 일 트래픽 제약(§2).
- 구현은 2026년 7월 28~29일에 진행한다.
