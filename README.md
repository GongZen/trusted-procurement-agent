# trusted-profit-agent

### 수익성 의사결정 Agent

> 기업 데이터를 분석해 **이익이 왜 변했는지** 진단하고, CEO가 **무엇을 먼저 결정해야 하는지**를
> 근거·반대증거·**결론이 뒤집히는 조건**과 함께 제시한다.
> 데이터가 갱신되면 보고 우선순위와 대응 방안을 다시 판정한다.

**현재 상태:** 문제 정의 · 설계 · 데이터 검증 완료 → **구현 2026-07-28~29**
**제출:** 2026 제1회 Upstage × BDAI Harness Engineering Skillthon

---

## 설계는 기능이 아니라 데이터에서 출발했다

만들고 싶은 기능을 먼저 정하고 데이터를 찾지 않았다. 순서를 뒤집었다.

**두 공개 데이터가 공통으로 무엇을 허용하는지 먼저 확정하고, 그 경계 안에서 답할 수 있는 질문을 골랐다.**

이 순서를 지킨 이유는 하나다. 데이터가 허용하지 않는 답을 그럴듯하게 만들어내는 순간, Agent는 신뢰를 잃는다.

### 1단계 — 경계를 먼저 그었다

대상은 재배포 가능한 공개 데이터 2종, **AdventureWorks**(Microsoft, MIT)와 **Contoso V2**(SQLBI, MIT)다.
두 데이터는 성격이 전혀 다르다. 한쪽은 제조·직판 중심 38개월치, 다른 쪽은 소매 유통 116개월치다.
**그럼에도 공통으로 존재하는 것만** 코어로 인정했다.

| | 두 데이터에 **공통으로 있는 것** | 그래서 계산할 수 있는 것 |
|---|---|---|
| 거래 | 라인 단위 수량 · 단가 · 원가 | 매출, 매출원가, **매출총이익** |
| 제품 | 제품 식별자 + 카테고리 계층 | 제품구성(믹스) 효과 |
| 고객 | 고객 식별자 + 거래 이력 | 반복구매·이탈 관점 |
| 기간 | 거래 일자 | 기간 비교, 추세 |
| 가격 | 할인 정보(형식은 다르나 양쪽 모두 분리 가능) | 실현가격, 할인 누수 |

| | 두 데이터에 **공통으로 없는 것** | 그래서 계산할 수 없는 것 |
|---|---|---|
| 판매관리비 | 없음 | 영업이익 · EBITDA 계열 분석 |
| 변동비 · 고정비 구분 | 없음 | 공헌이익 · **CVP 손익분기점** |
| 예산 · 목표 | 기준 단위가 서로 다름(한쪽은 영업사원별, 다른 쪽은 제품·매장별) | 계획 대비 실적 분석 |
| 재고 | 한쪽에만 있음 | 재고 기반 수익성 분석 |

**이 표가 이 프로젝트의 모든 설계 결정을 지배한다.**
특히 오른쪽 아래 — 변동비·고정비 구분이 없으므로 이 Agent는 **"손익분기점"이라는 표현을 쓰지 않는다.**

### 2단계 — 경계 안에서 답할 가치가 있는 질문

매출총이익까지만 계산할 수 있다는 제약은, 역설적으로 질문을 선명하게 만들었다.

> **이 제품군의 이익 변화에 대해 판가 · 원가 · 제품구성 중 무엇에 손댈 것인가.
> 그리고 지금 결정할 것인가, 더 볼 것인가.**

"이익이 줄었다"는 **현상**이지 질문이 아니다. CEO가 실제로 서명하는 것은 현상이 아니라 **행동**이다.
그래서 이 Agent의 출력은 진단 결과가 아니라 **결정 카드(Decision Card)**다.

## 고객 데이터가 있다는 것이 왜 결정적인가

마진 분해는 **"무엇이 변했나"까지만** 답한다. 가격이 내렸는지, 원가가 올랐는지, 많이 팔았는지, 잘 팔리는 제품 구성이 바뀌었는지.

**여기에 구조적인 사각지대가 있다.** 수량이 줄었을 때,

- 가격이 비싸서 안 팔린 것인지
- 고객이 떠난 것인지

**마진 등식 안에서는 이 둘을 구분할 수 없다.** 양쪽 모두 "수량 감소"라는 똑같은 숫자로 나타나기 때문이다.
그런데 대응은 정반대다. 앞은 **가격 정책**의 문제고, 뒤는 **고객 관계**의 문제다.

두 공개 데이터가 **모두 고객 식별자와 거래 이력을 갖고 있다는 사실**이 여기서 결정적이다.
같은 수량 감소를 놓고 *"가격 문제인가 고객 문제인가"*를 판정할 수 있게 해준다.
반복 구매 비율은 두 데이터에서 각각 **37.1%**와 **93.4%** — 시장 성격이 극단적으로 다르다.
같은 판정 로직이 이 두 곳에서 모두 작동한다면, 그것이 일반화의 가능성이 된다.

**단, 규율 하나를 함께 지킨다.**

> **마진 분해와 중복되는 고객 신호는 쓰지 않는다.**

실제로 한 번 걸러냈다. 처음에는 "활성 고객 수 추세"를 보조 지표로 쓰려 했으나,
**활성 고객 수와 주문 건수의 상관계수가 0.999969 / 0.999258**로 나왔다.
수량 효과를 고객이라는 다른 이름으로 반복하는 것에 지나지 않았고, 그래서 철회했다.
고객 데이터를 쓰는 것 자체가 목적이 아니라, **마진식이 답하지 못하는 것만** 고객 데이터에 묻는 것이 목적이다.

## 원인을 알려주는 것만으로는 결정이 되지 않는다

가장 유력한 원인을 짚어주는 도구 만으로는 부족하다.

> "원가가 주범인 건 알겠다. **그런데 그 판단이 틀릴 수 있는 조건은 무엇인가?
> 지금 움직여야 하나, 한 분기 더 봐야 하나?**"

원인만 알려주는 도구는 계산기다. **계산기와 판단의 경계가 정확히 이 지점**이다.

### 그래서 Decision Boundary

이 Agent는 결론과 함께 **그 결론이 뒤집히는 조건**을 제시한다.

- 원가가 얼마나 더 오르면 권고가 바뀌는가
- 판가를 얼마나 내리면 지금의 결론이 무효가 되는가
- 수량이 어느 선까지 회복되면 대응이 불필요해지는가

**여기서 임의의 임계치를 쓰지 않는다.** *"위험도 70% 이상이면 경고"* 같은 숫자는 근거가 없고, 근거가 없는 숫자는 설명할 수 없다.
대신 **권고가 뒤집히는 지점을 데이터에서 역산한다.** 경계까지 남은 여유(headroom)가 곧 확신도가 된다.

> 설계 원칙: **임계치를 임의로 정하는 것이 문제라면, 임계치를 없애는 것도 해법이다.**

## 설계 원칙

| 원칙 | 이유 |
|---|---|
| **숫자는 코드가, 설명은 LLM이** | LLM이 수치를 지어내지 못하게 한다. 계산 결과는 재현 가능해야 한다 |
| **검증을 산출물의 일부로** | 스키마·기간·키 중복·산식 대사를 `ValidationReport`로 함께 낸다. 데이터 품질은 부록이 아니다 |
| **모르는 것은 모른다고 쓴다** | 계산 범위를 벗어난 값은 추정하지 않고 **미확인(Unknowns)**으로 표시한다 |
| **같은 입력은 같은 결론** | 실행할 때마다 권고가 흔들리면 의사결정 도구가 아니다 |
| **설명할 수 없으면 채택하지 않는다** | 통계적으로 우수해도 판단 근거를 사람이 설명하지 못하면 감점 요인으로 취급한다 |

## 스스로 깬 전제

이 프로젝트에서 가장 많은 시간을 쓴 일은 **스스로 세운 전제를 검증하고 기각하는 것**이었다. 세 가지가 실제로 뒤집혔다.

### 1. "두 데이터에서 원가는 같은 뜻이다" → 기각

양쪽 모두 단위원가 컬럼이 있으니 공통 스키마로 묶을 수 있다고 봤다.
검산 결과 **정의가 달랐다.** 한쪽은 제품 마스터의 **표준원가**(계획된 원가), 다른 쪽은 판매 거래에 기록된 **실제 거래원가**다.
같은 필드로 적재하면 원가 차이를 마진 변동으로 오해하게 된다.

→ 공통 스키마를 포기하고, **원가의 의미를 메타데이터(`cost_basis`)로 명시**하는 구조로 전환했다.

### 2. 데이터셋 교체

쓰려던 Contoso 데이터에 **오픈 라이선스가 없었다.** 별도 조건이 없으면 개인·비상업 이용으로 제한되는 자료였고, 로컬 사본에는 출처·버전 기록조차 없었다.

→ **SQLBI가 MIT로 배포하는 Contoso V2**로 교체하고, URL·버전·SHA-256·다운로드일을 [DATA_SOURCES.md](DATA_SOURCES.md)에 기록했다.

### 3. "활성 고객 수 추세를 보조 지표로" → 철회

마진과 다른 각도를 보여줄 지표로 채택하려 했다. 검증 결과 **주문 건수와 상관계수 0.999969 / 0.999258**.
사실상 같은 정보의 반복이었다.

→ 철회하고, 대체 지표를 **과거 구간 학습 · 이후 구간 검증(holdout)** 방식으로 판정 중이다.
기준 모형(직전 기간 · 전년 동기)보다 나은 예측력을 보이지 못하면 채택하지 않는다.

## 한계

정직하게 남긴다. 이 한계를 숨기지 않는 것이 이 Agent의 설계 목표이기도 하다.

- **매출총이익 수준까지만** 다룬다. 두 데이터에 판매관리비가 없어 영업이익·EBITDA는 계산할 수 없다.
- **손익분기점을 계산하지 않는다.** 변동비·고정비 구분이 없는 데이터에서 CVP를 주장하는 것은 과장이다.
- 공개 샘플 데이터이므로 **실제 기업의 의사결정 결과와 대조 검증할 수 없다.**
- 구현은 2026년 7월 28~29일에 진행한다. 현재는 설계·검증 단계다.

## 협업 방식

이 저장소는 **사람 1명 + AI 2개(Claude · Codex)** 체제로 운영한다.

- 작업은 GitHub Issue로 배정하고, 각 AI는 전용 worktree에서 Issue별 브랜치로 작업한다.
- 담당 AI가 PR을 올리면 **상대 AI가 먼저 검토**한다.
- 상대 AI가 통과시킨 PR만 사람이 최종 승인하고 `main`에 병합한다.
- 검토 판정 근거는 PR에 남긴다. 커밋 이력 자체가 판단 과정의 기록이 된다.

AI가 만든 부분은 커밋에 `Co-Authored-By`로 표기한다.
