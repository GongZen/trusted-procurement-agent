# trusted-procurement-agent

### 식자재 조달 **점검 우선순위**를 정하는 Agent

> 매일 아침, 취급 품목 전부를 훑어 **"오늘 먼저 봐야 할 것"** 몇 개를 골라
> *왜 이상한지 · 어느 유통 단계에서 벌어졌는지 · 대체할 게 있는지 · 어디가 싼지*를
> 근거와 함께 한 장으로 낸다.

**쓰는 사람** — 기업의 **구매·조달 담당자**. 매일 수십 품목의 시세를 확인해야 하지만 전부 볼 시간은 없는 사람.

**현재 상태:** 데이터 소스·품목 범위 확정 → **구현 2026-07-28~29**
**제출:** 2026 제1회 Upstage × BDAI Harness Engineering Skillthon

---

## 1. 왜 「결정」이 아니라 「점검 우선순위」인가

조달 결정은 시장가격만으로 내려지지 않는다. **계약가격·구매량·재고·사용속도** 같은 내부 정보와 **품질규격·납기실적·대체 공급처** 같은 공급자 정보가 함께 필요하다.

공공데이터에는 **외부 정보(시장가격·물량·지역·계절)밖에 없다.**

그래서 결정을 대신하지 않는다. 대신 **결정 전에 무엇을 먼저 검토해야 하는지**를 정한다. 이것이 현재 데이터로 정직하게 도달할 수 있는 지점이다.

| 조달이 Agent에 맞는 이유 | |
|---|---|
| 반복 | 매입은 주 단위·월 단위로 계속된다 |
| 판단 근거 | 직관과 관행이 아니라 데이터로 설명한다 |
| 독립성 | **외부 공개데이터만 쓴다** — 기업 내부 데이터에 의존하지 않아 누구에게나 같은 품질로 동작한다 |

---

## 2. 쓰는 사람이 묻는 것

**갈래를 데이터에서 역산하지 않았다.** 식자재를 사는 사람이 실제로 하는 고민에서 출발했다.

| # | 조달 담당자의 질문 | 우리가 답하는 것 |
|---:|---|---|
| 1 | *"이번 주 뭐가 비싸졌지?"* | 취급 품목을 훑어 **평년 대비 이탈이 큰 품목**을 골라낸다 |
| 2 | *"이 가격이 비싼 건가?"* | 같은 등급·시장 기준에서 **평년 어디쯤인지** |
| 3 | *"어느 단계에서 오른 거지?"* | 🔑 **산지 → 도매 → 소매 중 어디서 벌어졌는지** |
| 4 | *"얼마나 갈까?"* | 과거에 같은 수준으로 오른 적이 **몇 번이고 각각 며칠 갔는지** |
| 5 | *"대신 쓸 게 있나?"* | 대체 품목·**대체 원산지**의 현재 가격 |
| 6 | *"어디서 사면 싼가?"* | 시장·지역·**도매법인** 간 가격차 |

### 답하지 않는 것

| 질문 | 왜 |
|---|---|
| *"이 품목을 계속 취급할까"* | 내부 수익성 데이터가 필요하다 |
| *"적정가는 얼마인가"* | 규범적 기준이 없다. **분포상 위치**만 말한다 |
| *"앞으로 오를까 내릴까"* | 예측 근거를 확보하지 못했다 ([DATA_CRITERIA §6](DATA_CRITERIA.md)) |
| *"이 공급처가 믿을 만한가"* | 품질규격·납기실적 데이터가 없다 |

### 🔴 「업무 영향」은 우리만으로 계산되지 않는다

```
업무 영향 = 가격 이상 × 내 구매량 × 재고 소진 위험 × 대체 가능성
            ─────────                                ─────────
            우리가 안다      내부 정보 — 없다          우리가 안다
```

그래서 산출물은 *"이것이 당신에게 얼마나 중요하다"*가 아니라 **"이것이 평소와 다르니 당신이 판단하라"**에 머문다. 다만 **취급 품목 목록만 받으면 절반은 메워진다.**

## 3. 유통 3단계를 관통한다

```
산지공판장  ──①──  도매시장  ──②──  소매
  45곳              가락·엄궁 등        대형유통·전통시장
```

**두 구간을 서로 다른 방식으로 잇는다.**

| 구간 | 결합 | 상태 |
|---|---|---|
| ① 산지 ↔ 도매 | **품목 코드가 같아 그대로 이어진다** | ⭕ 실측 확인 — 대분류 8개 일치, 불일치 0 |
| ② 도매 ↔ 소매 | 코드 체계가 달라 **사람이 만든 대응표**가 필요 | ⚠️ **61종만 대응 완료** |

근거와 대응표 규칙: [DATA_CRITERIA §3](DATA_CRITERIA.md)

### 이것이 만드는 차이

> ⚠️ **아래 숫자는 구조를 설명하기 위한 가상 예시다.** 실제 판정 규칙과 임계는 아직 정하지 않았다.

```
[가상 사례 1] 배추가 평년의 2.1배
   산지 1.9 · 도매 2.1 · 소매 1.8
   → 산지 단계에서 이미 벌어져 있다

[가상 사례 2] 사과가 평년의 1.6배
   산지 1.0 · 도매 1.6
   → 산지는 평년 수준인데 도매에서 벌어졌다
```

**같은 배수라도 「어디서 벌어졌는지」가 다르다.** 가격 하나만 보면 구분되지 않는 것이고, 여기서 확인할 것이 갈린다 — 앞은 **공급 쪽**을, 뒤는 **다른 법인·시장**을 본다.

> 🔴 **원인을 단정하지는 않는다.** 단계별 위치는 관측이지만 *"왜 그런가"*는 이 데이터만으로 확정되지 않는다.
> 산출물은 **어느 단계에서 벌어졌는지 표시하고, 무엇을 확인해야 하는지 제시**하는 데까지다.

## 4. 산출물 — 시장 보고서가 아니라 **예외 보고 한 장**

매일 전 품목 시세표를 주면 읽지 않는다. **오늘 이상한 몇 개만** 정해진 순서로 낸다.

| 순서 | 항목 |
|---:|---|
| 1 | **우선 검토 품목** — 평년 대비 이탈이 큰 순 |
| 2 | **이상 근거** — 평년의 몇 배 · 며칠째 · 어느 등급·시장 기준 |
| 3 | **예상 영향** — 취급 품목 중 해당 개수 (목록이 있을 때) |
| 4 | **가능한 대응** — 대체 품목 · 더 싼 시장·법인 · 유통 단계 전환 |
| 5 | 🔑 **추가 확인 사항** — **우리가 모르는 것을 명시한다**(재고·계약가·납기) |
| 6 | **판단 시한 참고** — 과거 같은 급등이 며칠 지속됐는지 |

**5번이 이 산출물의 성격을 정한다.** 모른다는 것을 감추지 않고, **무엇을 확인해야 판단할 수 있는지**를 알려준다.

### 층 구조 — 입력이 없어도 완주한다

```
0층 · MVP · 입력 없음     지원 품목 전체에서 이상 품목을 골라낸다
1층 · MVP · 품목 목록만   "내가 쓰는 품목" 안에서만 골라내고, 예상 영향의 절반이 채워진다
2층 · 범위 밖             매입가까지 넣으면 내 가격의 분포상 위치를 판정
```

**0층만으로 MVP가 성립한다.** 0층은 *조회*가 아니라 **선별**이다 — 무엇을 물어야 할지 모를 때 **시스템이 볼 것을 정해준다.**

## 5. Skill — 무엇을 자동화하나

분석 과정 전체를 **명령 하나로 재실행할 수 있는 단위**로 묶는다.

| 요구 | 이 Skill의 답 |
|---|---|
| **입출력이 명확한가** | 단계마다 JSON으로 주고받고 `schema_version`을 갖는다 |
| **재현되는가** | 계산은 코드가 한다. **같은 입력이면 같은 결과.** LLM은 설명만 쓴다 |
| **자동화되는가** | 수집 → 검증 → 기준선 산출 → 이탈 선별 → 심화 조사 → 예외 보고가 한 번의 실행으로 이어진다 |
| **검증은** | 별도 절차가 아니라 **Skill의 일부**다. 미조사일·미매칭 품목을 *미확인* 항목에 반영한다 |
| 🔑 **키 없이도 도는가** | **`sample-data/`에 수집 스냅샷을 넣어 인증키 없는 환경에서도 전 과정이 실행된다** |

**표준 폴더 구조를 따른다.**

```
skills/data-analysis/
├── skill.md          스킬 설명 및 사용법
├── README.md         개발자용 문서
├── reference/        지표·판정 규칙 정의
├── scripts/          collect · clean · analyze · plot
├── templates/        산출물 서식
├── examples/         사용 예시
├── sample-data/      수집 스냅샷 (키 없이 실행용)
└── config/           지원 품목 · 대응표 · 판정 기준
```

## 6. Agent — 조건에 따라 다음 조사를 정한다

**모든 품목에 같은 계산을 돌리면 대시보드다.** Agent는 **이상한 것만 골라 파고든다.**

```
1단계  스캔      취급 품목을 얕게 훑어 이상 후보만 추출
2단계  심화      🔑 이상 후보에 대해서만, 어느 도구를 쓸지 정해 조사한다
3단계  종합      왜 이상한지 + 그래서 무엇을 할 수 있는지
```

**2단계에서 조사 결과에 따라 다음에 볼 것이 갈린다.**

| 관측 | 산출물이 제시하는 것 |
|---|---|
| 가격↑ + **산지에서 이미 상승** | *"산지 단계에서 벌어졌다"* → 공급 쪽 확인 항목을 붙인다 |
| 가격↑ + **산지는 평년 수준, 도매만 상승** | *"도매 구간에서 벌어졌다"* → 다른 법인·시장 가격을 함께 낸다 |
| 가격↑ + **법인 간 편차 큼** | 법인별 가격을 나열한다 — **바로 행동 가능** |
| 가격↑ + **대체 원산지는 평년 수준** | 대체 원산지 가격을 나란히 낸다 |

> **원인을 확정하지 않는다.** 관측된 위치를 표시하고 **확인할 것을 제시**한다.
> 판정 임계와 분기 규칙은 아직 정하지 않았다 — 다음 단계에서 잠근다.

**트리거** — `schedule` 설정으로 매일 아침 자동 실행. 본체 소스가 일별 갱신이라 트리거를 인위적으로 만들 필요가 없다.

**진행 표시** — Agent가 무엇을 조사 중인지 실시간 체크리스트로 보여준다. *"이상한 것만 골라 파고든다"*가 화면에 드러난다.

**사람이 필요한 사안** — 자동으로 확정하지 않되 **루프를 멈추지도 않는다.**

> **Agent는 사람이 없어도 계속 돈다. 다만 사람이 결정해야 할 것을 표시한다.**

## 7. 설계 원칙

| 원칙 | 이유 |
|---|---|
| **계산은 코드, 설명은 LLM** | LLM이 수치를 지어내지 못하게 한다 |
| **검증을 산출물의 일부로** | 결측·미매칭을 숨기지 않는다 |
| **모르는 것은 모른다고 쓴다** | 재지 않은 것을 확정값처럼 쓰지 않는다. **「미측정」·「원인 미상」을 그대로 표기** |
| **같은 입력은 같은 결론** | 실행할 때마다 권고가 흔들리면 의사결정 도구가 아니다 |
| **설명할 수 없으면 채택하지 않는다** | 통계적으로 우수해도 근거를 설명하지 못하면 제외한다 |
| **재현할 수 없는 데이터는 쓰지 않는다** | 제3자가 자기 키로 같은 데이터를 받을 수 있어야 한다 |
| 🔑 **자동 매칭에 의존하지 않는다** | 품목 대응은 사람이 검수한다. `"배추" in "양배추"`가 참이라 실제로 틀렸다 |

## 한계

- **매입 시점을 권고하지 않는다.** 기상 지표로 가격 상승을 예측하려던 접근은 실측에서 기각됐다([DATA_CRITERIA §6](DATA_CRITERIA.md)). 과거 사례를 보여줄 뿐 *"사라/기다려라"*로 올리지 않는다.
- **품목 취급 여부를 판단하지 않는다.** 내부 수익성 데이터가 없다.
- **수요·소비량 데이터가 없다.** 두 포털에 존재하지 않는다.
- **정부 수급조절(비축·방출) 물량을 반영하지 못한다.** API가 없다.
- **3단계 분석은 61품목에서만 된다.** 30품목은 산지·도매 2단계까지다([DATA_CRITERIA §4](DATA_CRITERIA.md)).
- **일 트래픽 10,000회 제약**이 있어 수집 범위를 나눠야 한다.
